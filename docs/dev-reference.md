# 開発手引き

## TDD

TDDは、「動作するきれいなコード（Kent Beck "Clean code that works"）」の実装手法。  
次の5ステップからなる（[Kent Beckによる定義](https://t-wada.hatenablog.jp/entry/canon-tdd-by-kent-beck)）。

1. テストリスト
   - 期待する振る舞いを分析する
   - ×: 実装の設計判断を行う
2. ひとつテストを書く
   - 論理設計（インターフェース）を判断する
   - ×: コードカバレッジのために検証のないテストを書く
   - ×: 全てのテストを一度に書こうとする
3. テストを成功させる
   - 新しいテストの必要性に気づいたら、テストリストに追加する
   - ×: 検証を削除して、テスト成功のように見せる
   - ×: テスト対象の実行結果を検証の期待値にコピペする
   - ×: リファクタリングする
4. 必要に応じてリファクタリングを行う
   - 物理設計（内部実装）を判断する
   - ×: 必要以上にリファクタリングする
   - ×: 早すぎる抽象化。重複はヒントであって、指令ではない
5. テストリストが空になるまでステップ2に戻って繰り返す

論理設計と物理設計のステップ分割がポイント。

### 役割分担

設計判断に注力して、実装・リファクタリングは AI に委譲する。

| ステップ | 注力 | AIに委譲 |
|---|---|---|
| 1. テストリスト | テストケース作成 | |
| 2. ひとつテストを書く | 最も重要なテスト実装(論理設計) | 定型的なテスト実装 |
| 3. テストを成功させる | | 実装 |
| 4. リファクタリング | リファクタリング判断「いつ複雑化（↔︎単純化）するか」(物理設計) | リファクタリング |

## ドキュメント運用

| 種別 | ユースケース | ライフサイクル |
|---|---|---|
| GitHub Issues | 課題整理 | 永続 |
| test-list.md | テストリスト、雑多な気づき | ~実装完了（PRにコピペして削除） |
| ADR | 意思決定の記録 | 永続 |

### ADR

例：
```
## 結論
Repositoryを導入しない

## 理由
データソースが1つ、当面増えない

## 見直すタイミング
2つ目のデータソースが必要になったとき
```
